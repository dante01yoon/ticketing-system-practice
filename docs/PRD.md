# PRD — 콘서트 좌석 예매 1차 범위 (MVP)

## 목표
사용자가 공연을 고르고, 좌석맵에서 좌석 하나를 5분 동안 잡은(홀드) 뒤, 모의 결제로 예매를 확정할 수 있다.
결제는 두 단계다: 확정 요청이 결제 대기 예매를 만들고, 모의 결제사의 결과 콜백이 오면 그때 좌석이 팔린다.
같은 좌석이 두 번 팔리지 않는 것이 이번 범위의 핵심이다.

### 범위 밖
- **화면(프론트엔드)**: 이번에는 API만 만든다. 나중에 API 계약 파일에서 타입을 생성해 화면에 붙인다.
- 실제 로그인·회원가입, 실제 결제 연동(콜백 서명 검증 포함), 환불 실행·취소(환불 필요 **기록**까지만 한다), 공연·좌석 등록 API(시드 데이터로 준비), 대기열.

## 사용자 식별
로그인 대신 모의 사용자 헤더 `X-User-Id`를 쓴다. 홀드와 예매 확정은 이 헤더가 있어야 하며, 없으면 거절한다.
공연 목록과 좌석맵 조회는 헤더 없이도 된다.

## 좌석 상태 규칙
```
AVAILABLE ──홀드──▶ HELD ──(확정 요청 → 결제 대기 → 성공 콜백, 만료 전)──▶ SOLD
                     │
                     └─ 홀드 후 5분이 지나면 만료 (다시 홀드 가능)
```
- 홀드 시간은 **5분**이다. 만료 시각 = 홀드 시각 + 5분. 현재 시각 ≥ 만료 시각이면 만료다(5분 정각부터 만료, 4분 59초는 유효).
- 다시 홀드할 수 있는 좌석은 AVAILABLE이거나 **만료된 HELD**뿐이다.
- 만료되지 않은 HELD는 다른 사용자가 홀드할 수 없다.
- 자기 유효 홀드를 다시 홀드하면 성공으로 응답하되 **기존 홀드를 그대로 돌려준다(만료 시각을 늘리지 않는다)**. (열린 질문 2)
- **SOLD는 어떤 경우에도 다시 홀드하거나 판매할 수 없다.**
- 좌석맵에서 만료된 HELD는 AVAILABLE로 보인다. 만료 처리는 조회·홀드·확정·콜백 시점에 판단하며 별도 배치에 의존하지 않는다.

## 결제 흐름 (두 단계)
```
확정 요청(Idempotency-Key) ──▶ 예매 PENDING (좌석은 HELD 유지)
                                  │ 모의 결제사 콜백
                                  ├─ 성공, 홀드 만료 전 ──▶ 예매 CONFIRMED, 좌석 SOLD
                                  ├─ 성공, 홀드 만료 후 ──▶ 예매 REFUND_REQUIRED, 좌석은 팔지 않음
                                  └─ 실패 ──────────────▶ 예매 FAILED, 홀드는 만료 전까지 유지(새 키로 재시도 가능)
```
- **확정 요청**은 그 좌석을 홀드한 사용자가 만료 전에만 할 수 있고, 결제 대기(PENDING) 예매를 만든다. 이 시점에 좌석은 팔리지 않는다.
- 확정 요청에는 클라이언트가 만든 **멱등 키**가 있어야 한다. 같은 사용자가 같은 키로 다시 보내면 처음 응답을 그대로 돌려준다(좌석·예매 상태가 그 사이 바뀌었어도).
  같은 키를 다른 좌석에 쓰면 거절한다.
- 이미 예매가 있는 좌석에 **같은 사용자**가 (다른 키로) 다시 확정을 요청하면 새 예매를 만들지 않고 **기존 예매를 돌려준다**:
  확정된(CONFIRMED) 예매이거나, 아직 유효한 홀드에 묶인 결제 대기 예매일 때. (열린 질문 4) 다른 사용자는 기존 규칙대로 거절된다.
- **모의 결제사**는 실제 결제 대신 성공 또는 실패 결과를 콜백으로 보낸다. 테스트와 운영자가 콜백 API를 직접 호출해 결제사를 흉내 낸다. (열린 질문 3)
- 콜백은 결제 대기 예매에만 반영한다. 이미 결과가 정해진 예매에 오는 콜백(중복·뒤늦은 반대 결과)은 **아무것도 바꾸지 않고** 현재 예매를 돌려준다. 결과는 처음 반영된 콜백 하나로 정해진다.
- 성공 콜백이 **예매가 묶인 홀드의 만료 시각 이후에** 처리되면 좌석을 팔지 않고 예매를 환불 필요(REFUND_REQUIRED)로 기록한다. 그 사이 좌석을 다른 사람이 홀드했든 아니든 같다.
- 예매가 묶인 홀드의 만료 시각 = 확정 요청 시점의 홀드 만료 시각. 결제 대기 중에도 홀드 시간은 늘어나지 않는다.
- 한 좌석에 확정(CONFIRMED) 예매는 최대 하나다.

## 시각
- 홀드·만료·확정·콜백의 모든 판단과 기록 시각은 **서버 시각만** 쓴다. 클라이언트나 결제사가 보낸 시각은 판단에 쓰지 않는다.
- 같은 좌석에 대한 요청은 좌석 잠금을 얻은 **뒤의** 서버 시각으로 판단한다.

## 비기능 요구
- 같은 좌석에 홀드 요청이 동시에 들어와도 성공은 하나뿐이다. 확정 요청(예매 하나)과 콜백(반영 한 번)도 마찬가지다.
- 만료 판단에 쓰는 현재 시각은 테스트에서 바꿀 수 있어야 한다(5분을 실제로 기다리지 않는다).
- 스택: Python FastAPI · PostgreSQL. Redis 사용 여부는 구현 설계에서 정한다.

## 열린 질문
1. 한 사용자가 동시에 여러 좌석을 홀드할 수 있는가? (이번 범위는 "요청 하나에 좌석 하나"만 정함)

### 정한 질문 (6장)
2. 자기 홀드를 다시 홀드하면? → 성공으로 응답하고 기존 홀드를 그대로 돌려준다. 만료 시각을 늘리지 않는다.
3. 모의 결제 실패를 흉내 낼 방법? → 필요하다. 모의 결제사 콜백이 성공 또는 실패를 보낸다(US-05).
4. 이미 확정된 예매에 같은 사용자가 다시 확정을 요청하면? → 기존 예매를 돌려준다(거절하지 않음).
