# PRD — 콘서트 좌석 예매 1차 범위 (MVP)

## 목표
사용자가 공연을 고르고, 좌석맵에서 좌석 하나를 5분 동안 잡은(홀드) 뒤, 모의 결제로 예매를 확정할 수 있다.
같은 좌석이 두 번 팔리지 않는 것이 이번 범위의 핵심이다.

## 범위
| 포함 | 스토리 |
|---|---|
| 공연 목록 보기 | [US-01](stories/US-01-concert-list.md) |
| 공연의 좌석맵(좌석과 상태) 보기 | [US-02](stories/US-02-seat-map.md) |
| 좌석 하나를 5분 동안 홀드 | [US-03](stories/US-03-hold-seat.md) |

### 범위 밖
- **화면(프론트엔드)**: 이번에는 API만 만든다. 나중에 API 계약 파일에서 타입을 생성해 화면에 붙인다.
- 실제 로그인·회원가입, 실제 결제 연동, 환불·취소, 공연·좌석 등록 API(시드 데이터로 준비), 대기열.

## 사용자 식별
로그인 대신 모의 사용자 헤더 `X-User-Id`를 쓴다. 홀드와 예매 확정은 이 헤더가 있어야 하며, 없으면 거절한다.
공연 목록과 좌석맵 조회는 헤더 없이도 된다.

## 좌석 상태 규칙
```
AVAILABLE ──홀드──▶ HELD ──모의 결제 성공──▶ SOLD
                     │
                     └─ 홀드 후 5분이 지나면 만료 (다시 홀드 가능)
```
- 홀드 시간은 **5분**이다. 만료 시각 = 홀드 시각 + 5분.
- 다시 홀드할 수 있는 좌석은 AVAILABLE이거나 **만료된 HELD**뿐이다.
- 만료되지 않은 HELD는 다른 사용자가 홀드할 수 없다.
- **SOLD는 어떤 경우에도 다시 홀드하거나 판매할 수 없다.**
- 예매 확정은 그 좌석을 홀드한 사용자가 만료 전에만 할 수 있다.
- 좌석맵에서 만료된 HELD는 AVAILABLE로 보인다. 만료 처리는 조회·홀드 시점에 판단하며 별도 배치에 의존하지 않는다.

## 비기능 요구
- 같은 좌석에 홀드 요청이 동시에 들어와도 성공은 하나뿐이다. 확정도 마찬가지다.
- 만료 판단에 쓰는 현재 시각은 테스트에서 바꿀 수 있어야 한다(5분을 실제로 기다리지 않는다).
- 스택: Python FastAPI · PostgreSQL. Redis 사용 여부는 구현 설계에서 정한다.

## 다음 단계
- API 계약 파일(엔드포인트, 요청·응답 스키마, 오류 코드)은 별도로 작성한다. 이 문서와 스토리는 동작만 정하고 HTTP 상태 코드·필드 이름은 정하지 않는다.
- 작업 순서는 루트 `CLAUDE.md`의 「테스트 먼저(RED) → 구현(GREEN)」을 따른다.

## 열린 질문
1. 한 사용자가 동시에 여러 좌석을 홀드할 수 있는가? (이번 범위는 "요청 하나에 좌석 하나"만 정함)
2. 같은 사용자가 자기 홀드를 다시 홀드하면 만료 시각을 연장하는가, 그대로 두는가?
3. 모의 결제 실패를 흉내 낼 방법이 필요한가? (현재 가정: 모의 결제는 항상 성공)
4. 이미 확정된 예매에 같은 사용자가 확정을 다시 요청하면 기존 예매를 돌려주는가, 거절하는가?
