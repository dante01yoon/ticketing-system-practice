# US-05 모의 결제 콜백

**모의 결제사로서** 결제 결과(성공·실패)를 서버에 알리고 싶다. **그래서** 결제가 성공한 예매만 좌석을 판다.

실제 결제 연동은 없다. 테스트·운영자가 콜백 API를 직접 호출해 결제사를 흉내 낸다(PRD 열린 질문 3).
콜백은 사용자 헤더가 필요 없다. 콜백에 시각이 있어도 쓰지 않고, 판단은 콜백을 처리하는 순간의 **서버 시각**으로 한다.
"홀드 만료 시각"은 예매가 묶인 홀드의 만료 시각(= 확정 요청 응답의 결제 마감 시각)이다.

## 인수 조건
**AC-1 성공 콜백 → 판매**
- Given u1이 A1을 홀드하고 확정을 요청해 예매 B가 결제 대기다
- When 홀드 후 4분 59초에 B 성공 콜백이 온다
- Then B는 CONFIRMED, A1은 SOLD가 된다

**AC-2 실패 콜백**
- Given 예매 B가 결제 대기다
- When B 실패 콜백이 온다
- Then B는 FAILED, A1은 팔리지 않고 u1의 HELD로 남는다(만료 전까지, US-04 AC-12로 재시도 가능)

**AC-3 늦은 성공 콜백 → 환불 필요 (경계)**
- Given 예매 B가 결제 대기다
- When 홀드 후 5분 정각 또는 5분 1초에 B 성공 콜백이 온다
- Then B는 REFUND_REQUIRED로 기록되고 A1은 SOLD가 되지 않는다(좌석맵에서 AVAILABLE)

**AC-4 늦은 성공 콜백, 그 사이 다른 사람이 홀드**
- Given 예매 B가 결제 대기이고, 홀드 만료 뒤 u2가 A1을 홀드했다
- When B 성공 콜백이 온다
- Then B는 REFUND_REQUIRED, A1은 u2의 HELD로 남고 u2는 정상적으로 확정·결제할 수 있다

**AC-5 같은 콜백이 두 번 → 한 번만 반영**
- Given 예매 B가 결제 대기다
- When B 성공 콜백이 두 번(차례로 또는 동시에) 온다
- Then 두 번 다 성공으로 응답하고 B는 CONFIRMED, A1은 SOLD, 판매는 한 번뿐이다(확정 예매 하나)

**AC-6 결과가 정해진 뒤 반대 결과 콜백은 무시**
- Given B가 성공 콜백으로 CONFIRMED이다
- When B 실패 콜백이 온다
- Then 아무것도 바뀌지 않는다(B는 CONFIRMED, A1은 SOLD). 실패 뒤 성공 콜백, 환불 필요 뒤 성공 콜백도 마찬가지다

**AC-7 없는 예매**
- When 존재하지 않는 예매 ID로 콜백이 온다
- Then "예매 없음"으로 거절된다

**AC-8 콜백 형식 오류**
- When 결과 값이 성공·실패가 아니거나 예매 ID가 없는 콜백이 온다
- Then "요청 형식 오류"로 거절되고 아무것도 바뀌지 않는다

**AC-9 예매 상태 조회**
- Given u1의 예매 B가 있다
- When u1이 B를 조회한다 Then 현재 상태(PENDING·CONFIRMED·FAILED·REFUND_REQUIRED)를 받는다
- When 다른 사용자가 B를 조회한다 Then "예매 없음"으로 거절된다(남의 예매는 존재를 드러내지 않음)
