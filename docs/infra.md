# 7장 인프라 계약: 앱 3대 + Nginx

목표: 같은 이미지의 앱 세 대(app1·app2·app3) 앞에 Nginx 하나를 세워 `localhost:8080` 한 곳으로 받는다.
사용자별 속도 제한을 Nginx에서 걸고, 앱 하나가 죽어도 조회는 계속되며, 돈이 걸린 POST는 앱에 한 번 전달되면 Nginx가 다시 보내지 않는다.

## 파일과 소유 (7장 한정)

| 파일 | 소유 |
|---|---|
| `docker-compose.yml` (기존 `db` 서비스·5432 포트는 그대로 유지) | server |
| `deploy/app.Dockerfile` (빌드 컨텍스트는 저장소 루트, 기반 이미지·uv 버전은 고정 태그) | server |
| `deploy/nginx/nginx.conf` | server |
| `backend/` (X-App-Id 헤더 등) | server |
| `tests/infra/` | test |
| `docs/infra.md`, `docs/openapi.yaml` | lead |

## 구성

- `docker compose up -d --build` 한 번으로 `db`, `app1`, `app2`, `app3`, `nginx`가 뜬다.
- 앱 세 대는 같은 이미지, 환경 변수 `APP_ID`(`app1`/`app2`/`app3`)만 다르다. DB는 compose의 `db` 서비스.
- 호스트에 열리는 포트는 `8080`(nginx)과 기존 `5432`(db)뿐이다. 앱 컨테이너 포트는 호스트에 열지 않는다.
- 스키마·시드는 앱이 시작하며 만들지 않는다(세 대가 동시에 마이그레이션하면 경쟁한다). 지금처럼 호스트에서
  `reset_db`/alembic으로 만든다. 앱은 스키마가 이미 있다고 가정한다.
- DB 연결 예산: 앱 3대 × 워커 수 × (`DB_POOL_SIZE`+`DB_MAX_OVERFLOW`) + 테스트·마이그레이션 연결 < Postgres
  `max_connections`(100). 앱마다 워커 1개 또는 풀을 줄여 맞춘다(`backend/app/db.py` 주석 참고).

## ① 분배와 X-App-Id

- Nginx가 세 앱에 라운드 로빈으로 나눈다. Nginx 워커가 여럿이어도 고르게 나뉘도록 upstream에 공유 메모리 `zone`을 둔다.
- **모든 앱 응답**(성공·오류 모두)에 `X-App-Id: <APP_ID>` 헤더가 붙는다. Nginx는 이 헤더를 그대로 전달한다.
- Nginx가 직접 만든 응답(429, 502 등)에는 `X-App-Id`가 없다.

## ② 사용자별 속도 제한

- 키: `X-User-Id` 헤더 값. 헤더가 없으면 클라이언트 IP.
- 초당 5건, burst 10, `nodelay`(burst 안의 요청은 지연 없이 바로 처리).
- 넘으면 Nginx가 앱으로 보내지 않고 바로 답한다:
  - 상태 `429`, 헤더 `Retry-After: 1`, `Content-Type: application/json`
  - 본문 `{"code": "RATE_LIMITED", "message": "요청이 너무 많습니다. 잠시 뒤 다시 시도하세요."}`
- `X-User-Id`는 클라이언트가 정하는 모의 신원이라 값을 바꾸면 제한을 피할 수 있다. 공정한 분배 장치이지 악의적 트래픽 방어 수단이 아니다
  (진짜 방어는 실제 인증이 생긴 뒤의 일, 범위 밖).
- 제한은 모든 경로에 같이 건다. 429 판단은 앱의 401·400·422보다 먼저다(앱까지 가지 않으므로).

## ③ 장애 때 넘기기와 재시도

- 앱 하나가 죽으면(컨테이너 정지) 조회(GET)는 Nginx가 다른 앱으로 넘겨 클라이언트는 200을 받는다.
  정지 뒤 **10초 안에** 모든 GET이 나머지 두 앱에서 처리돼야 한다(연결 타임아웃·`max_fails`/`fail_timeout`을 그에 맞게 짧게).
- POST(홀드·확정·결제 콜백)는 **앱에 한 번 전달되면** Nginx가 다른 앱으로 다시 보내지 않는다. `proxy_next_upstream`에
  `non_idempotent`를 넣지 않는다. 전달 뒤 응답을 못 받으면(앱이 처리 중 죽는 등) 클라이언트는 Nginx의 5xx를 받는다.
- 앱에 **전달되기 전**(연결 수립 실패) POST는 다른 앱으로 넘겨도 된다. 어떤 앱도 받은 적이 없어 중복 처리가 없다(7장 결정, 사람 승인).
- 증거의 한계: 테스트는 설정 토큰(`non_idempotent` 부재)과 앱 정지 상태의 결과만 확인한다. '전달 뒤 응답 유실' 상황을 직접 만들어
  재전송이 없음을 보이는 동작 테스트는 없다.
- 클라이언트는 확정(`POST /bookings`)을 **같은 Idempotency-Key**로 다시 보내면 된다. 여러 번 보내도 예매는 하나이고,
  성공 응답은 모두 같은 예매 ID다(US-04 AC-9 멱등 규칙 그대로, 앱이 여러 대여도 DB 기준으로 지켜진다).
- 앱이 멈춘 상태에서도 Nginx는 설정 검사(`nginx -t`)·시작·재시작에 성공해야 한다. 앱 이름을 시작할 때 한 번만 해석하면
  멈춘 앱 이름을 찾지 못해 Nginx 전체가 뜨지 못한다(리뷰 P1). 앱 주소는 실행 중에 다시 해석하고, 멈췄던 앱이 다시 켜지면
  **30초 안에** 다시 요청을 받는다.
- 범위 밖: Nginx가 만든 502/504 본문을 우리 오류 모양으로 바꾸는 것, 헬스체크 엔드포인트 추가.

## 확인 (tests/infra)

1. 서로 다른 사용자로 GET 30번을 차례로 보내면 세 앱이 고르게 받는다(각 10건 근처).
2. 한 사용자가 30건을 한꺼번에 보내면 429가 나오고, 429는 위 헤더·본문 규칙을 지킨다. 다른 사용자는 영향이 없다.
3. `app2`를 멈춘 뒤 10초 안에 GET이 모두 app1·app3에서 200으로 처리된다.
4. `app2`가 멈춘 상태에서 같은 Idempotency-Key로 확정을 성공할 때까지 다시 보내면 DB에 그 좌석 예매는 하나뿐이다.
5. `app2`가 멈춘 상태에서 Nginx를 재시작해도 뜨고 GET이 app1·app3에서 처리되며, app2를 다시 켜면 30초 안에 app2도 받는다.
