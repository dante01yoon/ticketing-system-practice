# 8장 계약: Redis 캐시와 홀드 관문

목표: 세 앱이 같은 Redis 하나를 쓴다. 좌석맵 조회는 Redis 캐시로 DB 부하를 줄이고, 홀드는 Redis에서 먼저 걸러
이미 잡힌 좌석 요청이 DB(좌석 행 잠금)까지 가지 않게 한다.
**진짜 기준은 PostgreSQL이다.** Redis는 빠르게 거절하거나 빠르게 보여 주는 보조 장치일 뿐이며, Redis가 틀리거나 꺼져도
좌석이 두 번 팔리거나 PRD 규칙과 다른 결과가 나오면 안 된다.

## 파일과 소유 (8장 한정)

| 파일 | 소유 |
|---|---|
| `docker-compose.yml`(redis 서비스, 앱 환경 변수), `backend/` | server |
| `tests/cache/` | test |
| `pyproject.toml`·`uv.lock`(`redis` 패키지), `docs/cache.md`, `docs/openapi.yaml`, `docs/backend-interface.md`, `docs/infra.md` | lead |

## ① Redis 구성

- compose에 `redis` 서비스 추가: 이미지 고정 태그 `redis:7.4-alpine`, 호스트 포트 `6379:6379`(호스트에서 도는 테스트·앱이 쓴다).
- **순수 캐시로 띄운다**: `redis-server --save "" --appendonly no`. 멈췄다 켜면 내용이 비어야 한다(낡은 표시가 되살아나지 않게).
- 앱은 환경 변수 `REDIS_URL`을 쓴다. 기본값 `redis://localhost:6379/0`, compose의 app1~3은 `redis://redis:6379/0`.
- 앱은 Redis가 없어도 **시작에 성공**해야 한다(`depends_on`에 redis를 걸어도 되지만 healthy 조건으로 묶지 않는다).
- Redis 호출은 짧은 타임아웃(연결·명령 각 0.5초 이하)을 둔다. 연결 거부·타임아웃·기타 Redis 오류는 모두 "Redis 없음"으로 보고
  DB만으로 처리한다. Redis 오류가 클라이언트에 5xx로 나가면 안 된다.
- `backend.app.seed.reset_db()`는 DB와 함께 `REDIS_URL`의 Redis DB도 비운다(`FLUSHDB`). Redis가 꺼져 있으면 조용히 넘어간다.

## ② 좌석맵 캐시 (캐시 어사이드)

대상: `GET /concerts/{concert_id}/seats`의 200 응답만. 404는 캐시하지 않는다.

- 읽기: 캐시에 있으면 그대로 돌려주고 `X-Cache: HIT`. 없으면 DB에서 만들어 캐시에 넣고 `X-Cache: MISS`.
  Redis가 꺼져 있으면 DB에서 만들고 `X-Cache: MISS`. **모든 200 응답에 `X-Cache`가 있다.**
- HIT 응답 본문은 같은 시점의 MISS 응답 본문과 **바이트 단위로 같은 JSON 내용**이어야 한다(필드·순서·상태 표현 동일).
- TTL: **5초**(Redis 실제 시간). 5초가 지나면 다음 조회는 MISS.
- 지우기(무효화): 좌석 상태가 바뀌는 쓰기가 **DB 커밋에 성공한 뒤** 그 공연의 캐시를 지운다.
  - 홀드 201(새 홀드, 만료된 홀드 재홀드 포함)
  - 결제 성공 콜백으로 좌석이 SOLD가 될 때
  - 200 재홀드(변화 없음)·확정 요청(좌석 불변)·실패/환불 필요 콜백(좌석 불변)은 지우지 않아도 된다(지워도 틀리지는 않다).
- **만료로 바뀌는 좌석**: 만료는 배치 없이 시각으로 판단하고, 테스트는 `get_now`를 가짜 시각으로 옮기므로 Redis TTL로는 알 수 없다.
  캐시를 만들 때 그 공연의 유효 HELD 좌석 중 가장 이른 만료 시각(`get_now` 기준)을 함께 저장하고,
  읽을 때 `get_now() >= 그 시각`이면 캐시를 버리고(지우고) MISS로 다시 만든다. 즉 만료 판단 시점에 그 공연 캐시를 지운다.
- 받아들이는 한계: 조회가 커밋 전 DB를 읽은 뒤 쓰기의 캐시 삭제보다 늦게 캐시를 쓰면 최대 5초(TTL) 동안 낡은 좌석맵이 보일 수 있다.
  좌석맵은 안내용이고 홀드·확정 판단은 항상 DB로 하므로 판매 정합성에는 영향이 없다. 순차적인 "홀드 → 조회"는 반드시 새 상태를 본다.
  Redis가 꺼졌다 켜진 직후도 같은 이유로(①의 순수 캐시 설정 덕분에) 문제가 없다.

## ③ 홀드 관문 (Redis Lua)

`POST /seats/{seat_id}/hold`에서 401(X-User-Id) 검사 뒤, DB 트랜잭션을 열기 **전에** Lua 스크립트 하나로 원자적으로
"확인 + 표시"한다.

- 표시(marker): 좌석별 키 하나. 값에 홀드한 사용자와 만료 시각(`get_now` 기준 now + 5분)을 담는다. 키 이름·형식은 server가 정한다.
- Lua 입력: 좌석 ID, 사용자, 현재 시각(`get_now`). Redis 서버 시각(`TIME`)이나 Redis TTL로 만료를 판단하지 않는다.
- Lua 판단:
  1. 표시가 없거나, 표시의 만료 시각 ≤ 현재 시각이면 → 내 표시로 덮어쓰고 "통과".
  2. 표시가 나의 것이면 → 건드리지 않고 "통과"(자기 재홀드 200은 DB가 판단).
  3. 그 밖(다른 사용자의 유효 표시) → "거절". 앱은 DB에 가지 않고 **409 `SEAT_ALREADY_HELD`**(DB 거절과 같은 본문)로 답한다.
  - 판매된 좌석을 표시로 알고 있다면 거절 코드는 **409 `SEAT_ALREADY_SOLD`**여야 한다. **Redis 거절의 상태·`code`는 같은 순간 DB가 했을
    답과 같아야 한다.** 확실하지 않으면 거절하지 말고 DB로 보낸다.
- 통과한 요청은 지금처럼 DB(좌석 행 잠금, 잠금 뒤 시각)로 최종 판단한다.
- **되돌리기**: DB 결과가 201·200이 아니면(404·409·예외·5xx 등) 내가 이번 요청에서 쓴 표시를 지운다. 단 **값이 여전히 내 것일 때만**
  지운다(compare-and-delete, Lua). 다른 요청이 이미 덮어쓴 표시는 건드리지 않는다.
  DB가 "다른 사용자의 유효 홀드"를 알려 준 경우 지우는 대신 그 홀드(사용자·만료 시각)로 고쳐 써도 된다.
- **표시 수명(앱이 죽는 경우)**: Lua가 처음 쓰는 표시는 Redis 실제 시간으로 짧은 임대(30초 이하, PX)를 건다. DB 커밋 201 뒤
  표시를 확정해 홀드 만료 시각 기준으로 남긴다(실제 시간 PX는 5분 + 여유). 표시를 쓰고 DB 전에 앱이 죽어도 좌석이 최대 임대 시간만큼만
  잘못 거절된다.
- 좌석이 SOLD가 되면(성공 콜백) 표시를 판매 상태로 바꾸거나 지운다. 판매된 좌석에 남은 표시 때문에 `SEAT_ALREADY_SOLD` 대신
  `SEAT_ALREADY_HELD`가 나가면 안 된다.
- DB가 홀드를 받아들이면(201·200 모두) 표시를 DB의 실제 만료 시각(held_at + 5분)으로 바로잡는다(8장 리뷰 P1: 표시 없는 상태의
  자기 재홀드 200 뒤 now+5분 표시가 남아 DB 기준 만료 뒤에도 다른 사용자를 거절하던 결함).
- 판매 표시 쓰기가 실패하면 한 번 더 시도하고, 이미 CONFIRMED인 예매에 콜백이 다시 오면 판매 표시를 다시 쓴다.
  알려진 한계(받아들임): 재시도도 실패하고 중복 콜백도 없으면 판매된 좌석에 원래 홀드 표시가 그 홀드 만료까지(최대 5분) 남아
  `SEAT_ALREADY_SOLD` 대신 `SEAT_ALREADY_HELD`로 거절될 수 있다. 어느 쪽이든 거절이라 판매 정합성에는 영향이 없다.
  Redis 쓰기 하나만 실패하는 상황은 테스트로 재현하지 않는다(리뷰로 확인).
- 관측 헤더 `X-Hold-Gate`: 401 뒤의 모든 홀드 응답에 붙인다. Redis가 거절해 DB에 가지 않았으면 `REDIS`, DB 트랜잭션까지 갔으면 `DB`.
  Redis가 꺼져 있으면 모두 `DB`.
- 받아들이는 한계: Redis와 DB는 한 트랜잭션이 아니다. 그래서 Redis는 "확실히 안 되는 요청"만 일찍 거절하고, 성공은 언제나 DB가 정한다.
  Redis 표시가 남아 있어 잘못 거절하는 시간은 위 임대 시간과 되돌리기로 제한된다.
- 알려진 예외(받아들임): **존재하지 않는 좌석**을 두 사용자가 동시에 홀드하면, 앞 요청이 DB에서 404를 받고 표시를 되돌리기 전까지
  뒤 요청은 앞 요청의 표시 때문에 404 대신 409 `SEAT_ALREADY_HELD`를 받을 수 있다(앞 요청이 처리 중인 동안, 앱이 죽으면 임대 시간 동안).
  잘못된 좌석 ID에 대한 답만 달라질 뿐 판매 정합성과는 무관하다. 테스트는 이 경합을 검사하지 않는다(순차 404 뒤 표시가 남지 않는 것만 본다).

## ④ 확인 (tests/cache)

test가 먼저 쓰고(RED), lead가 해시를 기록한 뒤 server가 GREEN을 만든다. 필요한 Redis는 compose의 `redis`(localhost:6379).

1. 좌석맵 처음 조회는 `X-Cache: MISS`, 바로 다음 조회는 `HIT`, 두 본문은 같다. 5초가 지나면 다시 `MISS`.
2. 조회(캐시됨) → 홀드 201 → 바로 조회하면 그 좌석이 `HELD`로 보인다. 성공 콜백으로 SOLD가 된 뒤 바로 조회해도 `SOLD`.
   가짜 시각을 홀드 만료 시각으로 옮긴 뒤 조회하면 `AVAILABLE`.
3. 실서버(uvicorn 워커 2개 이상)에 서로 다른 사용자 200명이 같은 좌석을 동시에 홀드하면 201은 1건, 409 `SEAT_ALREADY_HELD` 199건이고,
   `X-Hold-Gate: DB`는 **1건**, `REDIS`는 199건이다. 비교로 Redis를 끈 상태의 같은 시험은 `DB` 200건(201 1건)이다.
4. 되돌리기: Redis를 비운 상태에서 A가 DB에 유효 홀드를 가진 좌석에 B가 홀드하면 409이고, A의 홀드 만료 시각이 되면 C의 홀드가
   201이다(B의 표시가 남아 C를 막지 않는다). 없는 좌석 홀드(404) 뒤에도 표시가 남지 않는다. 판매된 좌석 재홀드는 `SEAT_ALREADY_SOLD`.
5. **Redis를 멈춘 상태**(`docker compose stop redis`)에서 5장 동시성 테스트(`tests/concurrency`)가 그대로 통과하고, 좌석맵은 200 +
   `X-Cache: MISS`, 홀드 5xx 없음. 시험이 끝나면 반드시 redis를 다시 켠다.
6. 기존 테스트(`tests/api`, `tests/concurrency`, `tests/contract`)는 Redis가 켜진 상태에서도 그대로 통과한다.

`tests/cache`의 Redis 정지 시험은 `tests/infra`처럼 다른 자리의 테스트와 겹치지 않게 돌린다.

## 범위 밖

- Redis 클러스터·복제·Sentinel, 캐시 데우기, 공연 목록 캐시, 대기열.
- Redis를 홀드의 최종 기준으로 쓰는 설계(DB 없이 홀드 확정).
